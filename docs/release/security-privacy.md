# Security and privacy: what exists, what is missing

*Release candidate, Stage 5, 2026-10-18. Synthetic data only. Nothing here is a claim of HIPAA, CLIA, CAP, FDA or any other regulatory compliance; technical controls are not compliance.*

## Controls that exist and are tested
| Control | Where | Evidence |
|---|---|---|
| **One write path.** Every state change goes through `executeCommand`: zod input validation, then a server-side role check, then one transaction, then an append-only audit event. | `src/server/commands/registry.ts` | `tests/domain/*` (whole suite) |
| **Scoped idempotency.** A key belongs to one actor, lab scope, command and canonical request. The lookup, the command and the receipt run in one write-locked transaction. Any mismatch, another owner, a lost permission or an expired key is refused, and the stored result is never disclosed. A failed command leaves no receipt. | `src/server/core/idempotency.ts`, `registry.ts` | `tests/domain/security.test.ts` (20 cases, including two connections racing for one key) |
| **Fail-closed mode gate.** Outside `HLOS_MODE=demo` (or `next dev`), every user command is refused (401). The role switch (403), demo reset (404), design previews (404) and the simulated-source pump behind `GET /api/live` are all off. | `src/server/runtime-mode.ts`, API routes, `src/proxy.ts` | `security.test.ts` ("locked build", "GET /api/live") |
| **No internal actor over HTTP.** A user request can never act as `system`. Unknown or inactive staff ids are refused. | `registry.ts` | `security.test.ts` |
| **Presenter controls.** Commands marked `audience: "presenter"` (simulated world events, clock, outages, guided steps) are refused for the read-only demo roles and in locked builds. | `registry.ts`, `src/server/commands/*` | `security.test.ts` |
| **Correlation.** One correlation id per HTTP request, returned as `X-Correlation-Id` and written to every audit event and receipt of that request. | `src/server/session.ts`, `route.ts` | `security.test.ts` |
| **Append-only audit.** SQLite triggers forbid UPDATE and DELETE on `audit_event`. Approved gross content is frozen by a trigger. | `src/server/db/schema.sql` | `tests/domain/foundation.test.ts` |
| **Optimistic concurrency.** Version checks on edited records, or state guards on event-style transitions. A stale save shows both values and never overwrites. | `src/server/core/versioning.ts`, domain modules | domain tests, `tests/e2e/guards.spec.ts` |
| **Cross-origin refusal.** State-changing routes reject a browser `Origin` from another host. | `src/server/session.ts` | e2e |

## Production blockers (must exist before any real patient data)
1. **Authentication and authorization.** There is no sign-in. "Acting as" is a demo role cookie. Required:
   - the laboratory's identity provider (SSO/OIDC/SAML);
   - server sessions with expiry and automatic sign-out at shared bench workstations;
   - role assignment by an administrator;
   - break-glass rules;
   - re-authentication for consequential actions (accession, identity decisions, hold release).

   The locked mode exists so that no build can accidentally expose the demo role switch as a write path.
2. **Audit integrity beyond SQLite triggers.** The triggers stop the application, not someone with file access. Required:
   - append-only storage or hash chaining with external anchoring;
   - clock integrity (the demo clock is simulated);
   - retention and legal-hold rules;
   - an access log for reads, not only writes.
3. **Data protection.** Required:
   - encryption at rest and in transit, plus key management;
   - field-level minimization of patient data on bench screens;
   - de-identification for exports and screenshots;
   - a privacy review of every place a patient name is shown.
4. **Retention and deletion.** No policy exists. The demo reset deletes the whole database, which is acceptable only for synthetic data.
5. **Backup and recovery.** None. Required: encrypted backups, restore drills, and a paper downtime procedure tied to the worklist snapshot export.
6. **Real integrations.** Every connector is simulated (see `integration-readiness.md`). Each needs a contract, a test environment, error handling and monitoring before use.
7. **Command receipts.** These are now owner-scoped and expire after 24h (wall clock). Production still needs a cleanup job and monitoring of `IDEMPOTENCY_CONFLICT` events, which are audited as `command.idempotency_rejected`.
8. **Security testing.** No penetration test, dependency audit policy or threat model review has been done. The Stage 5 reviews were code reviews by the development team, not independent security assessments.
